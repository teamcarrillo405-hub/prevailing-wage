# Deploy Runbook — HCC Prevailing Wage

This runbook covers deploying to Render.com via the render.yaml Blueprint.
Run steps in order. Each section has a completion check.

---

## 1. Prerequisites

- Node.js >= 20 installed locally
- Render.com account with access to the `hcc-prevailing-wage` service
- GitHub repo access (Render pulls from `master` branch)
- All env var values ready (see Section 2)

Local build check before pushing:
```bash
npm run build        # must exit 0
npm run test         # must pass all tests
```

---

## 2. Env Var Checklist

Set these in Render Dashboard > Service > Environment before the first deploy.
All are marked `sync: false` in render.yaml — Render will NOT generate them.

| Variable | Where to Get It | Required |
|----------|----------------|----------|
| STRIPE_SECRET_KEY | Stripe Dashboard > Developers > API Keys | Yes (billing) |
| STRIPE_PRICE_PRO | Stripe Dashboard > Products > Pro plan price ID | Yes (billing) |
| STRIPE_PRICE_ENTERPRISE | Stripe Dashboard > Products > Enterprise plan price ID | Yes (billing) |
| STRIPE_WEBHOOK_SECRET | Stripe Dashboard > Webhooks > signing secret | Yes (billing) |
| ANTHROPIC_API_KEY | Anthropic Console > API Keys | Yes (AI classify) |
| RESEND_API_KEY | Resend Dashboard > API Keys | Yes (email) |
| APP_URL | `https://hcc-prevailing-wage.onrender.com` | Yes (SSO, emails) |
| SSO_SP_CERT | Generated SP certificate (PEM, single line) | Enterprise only |
| SSO_SP_KEY | Generated SP private key (PEM, single line) | Enterprise only |
| INVITE_CODE | Any string — gates registration | Yes |
| LOGTAIL_TOKEN | Better Stack > Sources > token | Recommended |

Auto-generated by Render (no action needed): `JWT_SECRET`
Hard-coded in render.yaml: `NODE_ENV`, `DATABASE_PATH`, `CORS_ORIGIN`

**SSO certificate generation** (one-time, for enterprise SSO):
```bash
openssl req -x509 -newkey rsa:2048 -keyout sp.key -out sp.crt -days 3650 -nodes -subj "/CN=prevailing-wage-sp"
# Set SSO_SP_CERT to contents of sp.crt (remove headers, single line)
# Set SSO_SP_KEY to contents of sp.key (remove headers, single line)
```

## 3. Disk Backup Procedure

Before any deploy that includes DB migrations, back up the SQLite file:

```bash
# From Render Shell (Dashboard > Service > Shell):
cp /var/data/prevailing-wage.db /var/data/prevailing-wage-$(date +%Y%m%d-%H%M).db
ls -lh /var/data/
```

Confirm the backup file exists before proceeding.

---

## 4. Render Rolling Deploy Steps

1. Push changes to `master` branch on GitHub
2. Render auto-detects the push and starts a new build
3. Monitor build in Render Dashboard > Service > Events
4. Build runs: `npm run build` (TypeScript compile + Vite client build)
5. On build success, Render starts the new instance
6. Health check: Render pings `GET /api/health` — must return 200 `{status:'ok'}`
7. If health check passes, traffic is switched to the new instance
8. Old instance is terminated

Manual trigger (if auto-deploy disabled):
```
Render Dashboard > Service > Manual Deploy > Deploy latest commit
```

---

## 5. Rollback Procedure

If the deploy fails or health check never passes:

1. Render Dashboard > Service > Events > find last successful deploy
2. Click "Rollback to this deploy"
3. Confirm rollback — Render restarts the previous build artifact
4. Verify health: `curl https://hcc-prevailing-wage.onrender.com/api/health`

If DB migration caused data corruption:
```bash
# Render Shell:
cp /var/data/prevailing-wage-YYYYMMDD-HHMM.db /var/data/prevailing-wage.db
# Then trigger a rollback deploy
```

## 6. Post-Deploy Smoke Test

Run after every deploy. All 7 checks must pass:

```bash
BASE=https://hcc-prevailing-wage.onrender.com

# 1. Health check
curl -s $BASE/api/health | grep '"status":"ok"'

# 2. Landing page loads (200)
curl -s -o /dev/null -w "%{http_code}" $BASE/ | grep 200

# 3. Auth endpoint reachable (POST returns 400 for empty body, not 404/500)
curl -s -o /dev/null -w "%{http_code}" -X POST $BASE/api/auth/login | grep 400

# 4. SSO metadata endpoint (200 XML)
curl -s -o /dev/null -w "%{http_code}" $BASE/api/sso/metadata | grep 200

# 5. Public API v1 reachable (401 for missing token, not 404)
curl -s -o /dev/null -w "%{http_code}" $BASE/v1/projects | grep 401

# 6. Webhook endpoint alive (405/400 for GET, not 404)
STATUS=$(curl -s -o /dev/null -w "%{http_code}" $BASE/api/billing/webhook)
[[ "$STATUS" == "400" || "$STATUS" == "405" ]] && echo "PASS" || echo "FAIL: $STATUS"

# 7. Static SPA served (index.html for unknown route)
curl -s $BASE/dashboard | grep -c "<div id=\"root\""
```

All 7 must succeed. Any failure: check Render logs > Service > Logs.

## 7. Known Limitations

- **OPS-02: No zero-downtime migration.** SQLite WAL mode is enabled but schema changes briefly lock the file. For migrations: deploy during off-hours (< 100ms lock for typical ALTER TABLE).
- **OPS-03: Single-instance SQLite.** Render free/starter tier runs one instance. Horizontal scaling requires migrating to Turso or Postgres — planned for v9.0.
- **Disk persistence:** The `/var/data` disk is Render-managed. It survives deploys and restarts but NOT service deletion. Back up before deleting the service.
- **SSO SP cert rotation:** Changing `SSO_SP_CERT`/`SSO_SP_KEY` requires updating the SP metadata in each IdP admin panel. Coordinate with enterprise admins before rotating.
